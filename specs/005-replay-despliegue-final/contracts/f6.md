# Contratos: cambios de F6

Base: `docs/referencias/CONTRATO-API.md` (prevalece), `specs/003-…/contracts/api-f4.md` y `specs/004-…/contracts/api-f5.md`. Todo es **aditivo**: sin `mode` ni `run`, las
respuestas de la API son las de F5. Fechas en milisegundos Unix UTC; `null` nunca NaN/Infinity. Errores `{ "error", "detail" }`.

## 1. Mensaje Kafka de replay (topic `terremotos.replay`, clave = `event_id`)

```json
{
  "source": "replay-historico",
  "mode": "replay",
  "ingested_at": 1794300000000,
  "event": { "type": "Feature", "id": "us6000abcd", "geometry": {"type": "Point", "coordinates": [-70.1, -33.4, 25.0]},
             "properties": {"mag": 4.6, "magType": "mb", "place": "…", "time": 1742000000000, "updated": 1742003000000, "type": "earthquake"} },
  "replay": { "run_id": "r-20261108-1", "seq": 7, "caso": null, "velocidad": 1200.0 }
}
```

| Campo | Regla |
|---|---|
| `mode` | siempre `replay`; el consumidor en vivo lo descarta con motivo y el de replay descarta `live` |
| `source` | `replay-historico` (el consumidor de replay no admite otro) |
| `ingested_at` | instante de reproducción; **no** sustituye al tiempo del evento |
| `event` | el GeoJSON de `historico.evento.raw`; `time` y `updated` **sin alterar** en los eventos reales. Los casos controlados llevan id propio `replay-ctl-<caso>` y copian los datos de un evento real; solo `revision` y `antigua` cambian `updated` (y la magnitud) en sus versiones |
| `replay.run_id` | identificador de la ejecución (texto) |
| `replay.seq` | orden de publicación dentro de la ejecución |
| `replay.caso` | nulo en eventos reales; en los casos controlados, uno de `duplicado`, `revision`, `antigua`, `magnitud_nula`, `coordenadas_invalidas`, `maritimo` |
| `replay.velocidad` | factor de aceleración (tiempo real cubierto / duración de la reproducción) |

Sin `event.id` válido o con coordenadas fuera de rango, el procesamiento lo manda a cuarentena con motivo (comportamiento de F3, sin cambios).

## 2. API: parámetro `mode`

| Parámetro | Endpoints | Regla |
|---|---|---|
| `mode` | `/api/eventos`, `/api/estadisticas`, `/api/salud` | `live` (por defecto) o `replay`; otro valor → 422 |
| `run` | los tres, solo con `mode=replay` | `run_id` de una ejecución; por defecto la de mayor `iniciada_at` (incluida una en curso); inexistente → 422; con `mode=live` → 422 |

Con `mode=replay`:

- Lee **solo** `replay.*` (nunca `live` ni `historico`); `start`, `end`, `min_mag`, `country_id`, `limit` y `offset` funcionan igual. Sin `start`/`end`, el periodo es el intervalo de la
  ejecución (`[desde, hasta + 1 ms)`), no «últimas 24 h», y así se indica en `metadata.period`.
- `metadata.mode` = `"replay"`; `metadata.replay` = `{run_id, estado, tamano, velocidad, intervalo: {desde, hasta}, iniciada_at, terminada_at}`; `metadata.coverage` = el intervalo de la ejecución.
- Cada `feature.properties` añade `caso` (nulo en reales) y `replayed_at` (ms); `mag` nula sigue siendo `null`. El panel muestra el distintivo «caso controlado / sintético» cuando `caso` no es nulo.
- `/api/estadisticas`: mismos bloques; `comparacion` = `{ "unit": "events", "comparacion_disponible": false, "motivo": "no_aplica_en_reproduccion", "historico": null, "variacion": null }`.
- `/api/salud?mode=replay`: los campos de F5 sin cambios (`last_ingestion` es la ingesta en vivo) más `replay` con la misma estructura que `metadata.replay`, o `null` si no hay ejecuciones.
- Sin ejecuciones: `200` con `features: []`, `total: 0` y `metadata.replay: null`; el panel lo explica.
- Misma política de errores: 503 si PostgreSQL falla.

Con `mode=live` (o sin `mode`) no aparece ningún campo de replay y el comportamiento es el de F5.

## 3. Configuración de despliegue (sin secretos)

| Elemento | Regla |
|---|---|
| `compose.yaml` | cinco servicios; puerto de la API `127.0.0.1:${API_PUERTO:-8000}:8000`; Kafka y PostgreSQL sin puertos publicados |
| `API_CORS_ORIGINS` | lista separada por comas con el origen exacto de Netlify (`https://<sitio>.netlify.app`) y `http://localhost:4200`; sin comodines; solo `GET`/`OPTIONS`; cabecera permitida `ngrok-skip-browser-warning` |
| ngrok | `ngrok http 8000` en el equipo; el authtoken está en la configuración propia de ngrok, nunca en el repositorio, en `.env.example`, en Angular, en `config.json`, en registros ni en evidencias |
| `config.json` publicado | un paso de build escribe `{ "mode": "api", "apiUrl": "https://<dominio-ngrok>", "refreshMs": 60000, "skipNgrokWarning": true }` en `public/config.json` **antes de compilar** y restaura el original después (se comprueba su hash); el repositorio conserva `http://127.0.0.1:8000` |
| Rutas expuestas | se enumeran las que salen por el túnel (incluidas `/docs`, `/redoc` y `/openapi.json` de FastAPI) y se decide cuáles quedan |
| Netlify | sirve el build estático de Angular; el navegador del visitante consulta la API por HTTPS |

Expuesto por el túnel: **solo** la API. Una prueba de 6.6 comprueba que `kafka:9092` y `postgres:5432` no son alcanzables desde fuera del equipo.
